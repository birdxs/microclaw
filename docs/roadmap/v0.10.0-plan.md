# MicroClaw v0.10.0 execution plan — Work ↔ Server pairing

Status: **Delivered**
Updated: **2026-10-18**

MicroClaw 0.10.0 opens Stage 4 of the Work roadmap: a MicroClaw Work desktop
client connected to a user-owned MicroClaw Server. The release delivers the
first, smallest useful slice of that stage and keeps everything else on the
existing local-first path.

## Scope

1. **Explicit device pairing with revocable credentials (Server).**
   An operator mints a short-lived pairing code in the Web console
   (Access tab) or over the API. A Work client claims the code once and
   receives a device token. Device tokens are hashed at rest, carry only
   `operator.read` + `operator.write`, show up as `device:<id>` actors in the
   audit log, and can be revoked from the Web console at any time.
2. **Remote task submission, progress, and cancellation (Server + Work).**
   Work submits a task to the Server's existing `send_stream` run model,
   follows progress over the existing SSE stream (with `last_event_id`
   replay on reconnect), and cancels through a new HTTP cancel endpoint.
   Approvals keep the "reply with the option value" semantics both products
   already share.
3. **Clear local-versus-remote execution in Work.**
   A new Server section in Work settings pairs/unpairs the client and shows
   the paired identity; the composer shows the active execution target
   (Local or Server) so a user always knows where a task runs and under
   which permission scope.
4. **Security Audit back to green.** zip 9 (deflate only), rustls 0.23.46,
   quinn-proto 0.11.19.

Out of scope for 0.10.0: Server-owned scheduling from Work, remote
artifacts/attachments, device-to-device discovery, and multi-tenant hosting.

## Server API contract

All endpoints live on the existing Web server and reuse `require_scope`.

| Method | Path | Scope | Body / Query | Response |
|---|---|---|---|---|
| `POST` | `/api/pairing/codes` | `operator.admin` | `{label?, expires_minutes? (1–60, default 10)}` | `{ok, code, expires_at, label}` |
| `POST` | `/api/pairing/claim` | none (code is the credential) | `{code, device_name, platform?}` | `{ok, device_id, device_token, label, scopes, server:{version}}` |
| `GET` | `/api/pairing/devices` | `operator.admin` | – | `{ok, devices:[{id, device_id, label, platform, prefix, created_at, last_seen_at, revoked_at}]}` |
| `DELETE` | `/api/pairing/devices/:id` | `operator.admin` | – | `{ok, revoked}` |
| `GET` | `/api/pairing/whoami` | `operator.read` | – | `{ok, actor, scopes, device:{device_id,label,platform}\|null, server:{version}}` |
| `POST` | `/api/runs/:run_id/cancel` | `operator.write`, run owner or admin | – | `{ok, run_id, aborted}` |

- Pairing codes are 8 characters from an unambiguous alphabet, kept in
  memory on the Server, single-use, and expire after `expires_minutes`.
  Claims are rate limited (10 failed attempts per minute, server-wide).
- Device tokens are `mcd_<32 hex>`; only `sha256(token)` is stored.
  They are presented as `Authorization: Bearer <token>` exactly like API
  keys. A revoked or unknown token yields `401`.
- Remote run protocol used by Work (unchanged Server endpoints):
  `POST /api/send_stream {session_key, sender_name, message}` →
  `{run_id}`; `GET /api/stream?run_id&last_event_id` (SSE events `status`,
  `tool_start`, `tool_result`, `delta`, `approval_required`, `file_diff`,
  `subagent_started`, `subagent_finished`, `checkpoint_created`,
  `plan_updated`, `process_output`, `mid_turn_injection`, `aborted`,
  `done`, `error`). Work maps these onto `RuntimeEventEnvelope` with a
  client-side sequence and feeds its existing session state machine.

## Work client

- `microclaw-work-runtime::remote` — `RemoteServerClient` (pair, unpair,
  whoami, submit, stream, cancel) and `RemoteRuntimeService::start`
  returning the same `WorkRunHandle` the embedded runtime returns.
- Credentials: `<work_data_root>/remote-server.json`, mode `0600`.
- Settings → Server: server URL, pairing code, Pair / Unpair, status line.
- Composer chip: `Local` / `Server · <label>`; cancellation and approvals
  work identically in both targets.
- `microclaw-work-headless server "<task>"` drives the same client for
  smoke tests.
